## What Works
<!-- Approaches, patterns, and solutions that have proven effective here -->
- 2026-09-01: when a redesign SHORTENS a visible button label, keep the old
  string as the button's `aria-label` and the flow's `find role button --name`
  keeps resolving with no flow edit. The eval run table now shows "Compare" but
  carries `aria-label={t("runList.compare")}` — "Compare selected runs" — which
  is the name flow 11 has always selected on. Chrome names a button from
  `aria-label` in preference to its text, so this is the cheap way to let the UI
  and a deterministic flow disagree on wording. The inverse also bit: the PASS
  cell's `"{passed}/{total} passed"` became a visually-hidden span next to a
  visible `"9/9"`, which `wait --text` still matches because clipped text stays
  in `textContent` — but the flow now asserts the visible `"0/9"` because that
  is the string a human reading the screen would check (evidence:
  client/src/app/evals/[agentId]/_components/EvalRunTable/EvalRunTable.tsx:77;
  e2e/specs/11-evals.flow.json compare + pass-tally steps)
- 2026-08-30: to reproduce a CI e2e failure locally in CI SHAPE without touching the running dev stack: `rsync -a --exclude node_modules --exclude .next client/ <scratch>/client-e2e/`, symlink `node_modules` back to the real one, then `NEXT_PUBLIC_API_BASE=http://localhost:<api> pnpm exec next build && pnpm exec next start -p <web>` in the copy, against an isolated `pgvector/pgvector:pg16` container and `pnpm exec tsx src/server.ts` on alt ports. The copy is required, not paranoia: `next build` and `next dev` share `client/.next`, so building in place while the dev server runs corrupts the shared cache (that is the recharts / routes-manifest failure recorded below). Note `scripts/e2e.sh` runs `next dev` while `e2e-web.yml` runs `pnpm build` + `pnpm start` — the hermetic script does NOT reproduce CI's build mode (evidence: scripts/e2e.sh:147; .github/workflows/e2e-web.yml "Build + start web (:3000)")
- 2026-08-24: `BriefVerdictStrip`'s counts badge composes from TWO adjacent i18n calls as JSX siblings — `{tVerdict("verdict.findingsCount", {count})}{tVerdict("verdict.blockers", {count})}` — with `verdict.blockers` = `" · {count} blockers"` (leading space baked in) rendered only when the live blocker count is `>0`; `wait --text` matches the concatenated result as one string, e.g. `"2 findings · 1 blockers"`. The blocker count itself is `composeBlockingReasons(...).length`, NOT `run.blockers` from the DB, and on seeded PR #482 it resolves to exactly 1 because the seeded review's `run_id` is null → `ci_fail_on` is null → `meetsGate` falls back to `'critical'` (AC-93) → only the CRITICAL finding (of 2 seeded findings, one CRITICAL one WARNING) counts. The merge-risk band composes as `{t("mergeRisk.label")}: {t("mergeRisk."+band)}` = `"Merge risk: Medium"` on #482 (`server/src/db/seed.ts:338`). Before writing a `wait --text` against this strip on a different seeded PR, re-derive both strings from `BriefVerdictStrip.tsx` + `helpers.ts` rather than assuming the shape (evidence: client/src/app/repos/[repoId]/pulls/[number]/_components/OverviewTab/_components/BriefVerdictStrip/BriefVerdictStrip.tsx:92,101-103; helpers.ts:49-64; client/messages/en/prReview.json `verdict.blockers`; server/src/db/seed.ts:505-543,1094)
- 2026-08-23: confirmed fix for the PR-row click race — one `{ "cmd": ["wait", "--load", "networkidle"] }` step between `wait --url "/pulls"` and `find text "Add rate limiting to public API endpoints" click` retires it: four consecutive hermetic runs of the full suite went 9/9 after inserting it in 04, 05 and 09, against a 7/9-8/9-9/9 flap before. Flow 02 never flapped on the identical click because it happens to assert `wait --text` on the row title first — that `wait --text` was doing the guarding, not luck. RULE: a `find` whose target comes from a fetch needs either `wait --load networkidle` or a `wait --text` on the target between it and the `wait --url` (evidence: e2e/specs/04-pr-findings.flow.json:7, 05-pr-diff.flow.json:7, 09-project-context.flow.json:37; 4x `E2E_PG_PORT=5441 E2E_API_PORT=3111 E2E_WEB_PORT=3110 npm run e2e:hermetic`)
- 2026-08-23: a sidebar `find text "Conventions"|"Project Context" click` straight after `wait --url "/pulls"` is NOT the same race and needs no settle — the nav labels come from the static `vendor/ui/nav.ts` array rendered by `AppFrame`, so they exist as soon as the shell mounts, independent of any repo/PR fetch. Only a locator whose text arrives with API data has to be guarded; auditing flows 01-09 for the unguarded pattern turned up nothing beyond 04, 05 and 09 (evidence: client/src/vendor/ui/nav.ts:34; client/src/components/app-shell/AppShell.tsx:22; e2e/specs/08-conventions.flow.json:7, 09-project-context.flow.json:7)
- 2026-08-23: when a flow asserts a next-intl message that interpolates the repo, assert ONLY the invariant head of the string. `context.attachedCount` renders as `0 attached · 4 in acme/payments-api` (the panel passes `activeRepo.full_name`, falling back to `context.repoUnknown` = "the selected repository"), so `wait --text "0 attached"` / `"1 attached"` still distinguishes before from after while staying off both the full repo name and the U+00B7 separator — a flow file that stays ASCII apart from the one deliberate em dash is easier to keep byte-exact (evidence: client/messages/en/agents.json `context.attachedCount`; client/src/components/doc-attach/DocAttachPanel.tsx:174; client/src/app/agents/[id]/_components/AgentEditor/_components/ContextTab/ContextTab.tsx:44)
- 2026-08-23: the run-trace drawer hides prompt text behind TWO independent collapses, and a flow must click both or `wait --text` times out on body text that is simply not in the DOM: the `Prompt assembly` `TraceSection` is `defaultOpen={false}`, and then EACH `PromptBlock` segment is separately collapsed (`useState(false)`) and renders its `<pre>` only when open. Both headers are `div`s with `onClick`, not buttons, so `find text "<label>" click` is the right locator for both. Asserting the segment's LABEL passes with only the first click — that is what makes the second one easy to miss (evidence: client/…/RunTraceDrawer/_components/PromptBlock/PromptBlock.tsx:70 `{open && <pre…>}`; TraceBody.tsx `TraceSection … defaultOpen={false}`; cost one red hermetic run on e2e/specs/09-project-context.flow.json)
- 2026-08-23: `find text "<label>" click` DOES work for a clickable non-button card — the agent cards on `/agents` are plain `<div onClick>` wrappers, and clicking the inner text bubbles to the card and navigates. This does not contradict the 2026-08-05 entry below: that one is about real `<button>`s, whose text locator resolves to a wide ancestor. Rule of thumb: `find role button --name` for buttons, `find text … click` for div-with-onClick cards and sidebar links (evidence: e2e/specs/09-project-context.flow.json "open the agent editor"; client/src/app/agents/_components/AgentCard/AgentCard.tsx:29)

## What Doesn't Work

  the target is off-screen — the failure then surfaces one step later as a
  `wait --url` timeout, pointing at the wrong step entirely. Flow 11's
  configure-cases click landed nowhere because the preceding compare-modal steps
  had scrolled the run table into view, leaving the header link above the

  The `eval` + `scrollIntoView({block:'center'})` step the file already used for
  three other controls fixed it, and the suite went 11/11 on CI. Centre anything

  e2e/specs/11-evals.flow.json; GitHub runs 33453822851 → 33454202635)
- 2026-09-01: `find role link` is the ONE locator that does not survive CI.
  Flow 11 was the only flow in the suite using it, and it is the only flow that

  `Element not found` while `find role button`, `find role checkbox` and
  `find text` pass across all 11 flows, and while the accessibility tree dumped

  Switching each to `find testid` moved the flow forward step by step — the

- 2026-09-01: `find role <role> --name` can fail with `Element not found` on CI

  role and name. Flow 11's agent link was captured by a `snapshot` step inserted
  immediately before the click — `link "Security Reviewer" [ref=e16]` — and the
  very next command still reported it missing. Excluded as causes: `next dev` vs
  a production build, agent-browser 0.33.2 vs 0.35.2 (what CI's UNPINNED
  `npm i -g agent-browser` installs), and the seed, all 11/11 locally. When a
  role lookup contradicts the snapshot, stop hardening the waits and move the

- 2026-08-30: ticking the two run checkboxes does NOT open the eval compare modal — it closes it. The agent eval page passes `onSelectionChange={(runIds) => { setSelectedRunIds(runIds); setCompareOpen(false); }}` and only `onCompare={() => setCompareOpen(true)}` ever sets it true, with the modal gated on `compareOpen && compareRunA && compareRunB`, so the `Compare selected runs` button (enabled at exactly two selected) is the only thing that opens it. A flow that selects two runs and then waits on the modal title hangs forever, and the seven compare assertions after it are dead. `find role button click --name "Compare selected runs"` goes between the second checkbox click and the `wait --text "Compare runs"` (evidence: client/src/app/evals/[agentId]/page.tsx:188-192,232; client/messages/en/eval.json `runList.compare`; e2e/specs/11-evals.flow.json)
- 2026-08-30: an eval suite run's Pass-column text (`"{passed}/{total} passed"`) is NOT a valid completion signal — the client renders it from `run.cases_passed ?? 0`, so a `running` row with `cases_passed: null` shows the exact same `"0/9 passed"` text as a genuinely `done` run where every case failed. `wait --text "0/9 passed"` right after clicking "Run eval" can resolve while the run is still in progress, and a second "Run eval" click then fails because the button still reads "Running…". Gate on a status-specific signal first — `EvalRunList`'s selection checkbox only renders `isSelectableForCompare(run)` = `run.status === 'done'`, so `wait --fn "document.querySelectorAll('[role=checkbox]').length===1"` (or `===2` for two runs) is the actual completion proof; only assert the Pass-column text *after* that (evidence: client/src/app/evals/[agentId]/_components/EvalRunList/EvalRunList.tsx:120 `passed: run.cases_passed ?? 0`; helpers.ts:18-19 `isSelectableForCompare`; live-verified against a running dev stack, GET /agents/:id/eval-runs showing `status:"running", cases_passed:null` while the UI text already read as if zero-passed)

- 2026-08-31: correction to the three eval entries in this file that cite `client/src/app/evals/[agentId]/page.tsx` — that page is now a `redirect()` to `/agents/<agentId>?tab=evals`, and every component and behaviour they describe moved to `client/src/app/agents/[id]/_components/EvalsTab/`. - 2026-08-31: `document.querySelectorAll('[role=checkbox]')` stays scoped to `EvalRunList`'s run-selection boxes even now that the eval surface renders inside the agent editor, whose left-hand agent list draws an enabled/disabled toggle per agent — `@devdigest/ui`'s `Toggle` is a `<button role="switch">`, not a checkbox, so the `length===1` / `length===2` completion gates in flow 11 are not polluted by the five seeded agents in that list. Check the primitive's role before reusing a bare `[role=…]` count on a page you have just moved a component onto (evidence: client/src/vendor/ui/primitives/Toggle.tsx:15 `role="switch"`; client/src/app/agents/_components/AgentCard/AgentCard.tsx `<Toggle …>`; e2e/specs/11-evals.flow.json)
- 2026-08-30: two `EvalRunList` run-selection checkboxes can share an identical accessible name — `"Select run from {time}"` where `{time}` is `relativeTime(started_at)`, and two runs started seconds apart both round to e.g. "just now". `find role checkbox --name "Select run from ..."` is therefore ambiguous for a two-run compare flow; use `find nth 0 "[role=checkbox]" click` / `find nth 1 ...` instead (raw CSS attribute selector, table row order is stable across re-renders). The same duplicate-name trap exists for `EvalCaseList`'s "New case" button (rendered once in the header, again in the empty state, identical text) — but it self-resolves for any flow that reaches the case list only after the agent already owns eval cases (e.g. the seeded `Security Reviewer`'s 8+ cases), since the empty-state copy only renders when `cases.length === 0` (evidence: client/src/app/evals/[agentId]/_components/EvalRunList/EvalRunList.tsx:98 `t("selectRun",{time})`; EvalCaseList.tsx:32,40 two `t("newCase")` buttons; helpers.ts `isSelectableForCompare`)
- 2026-08-30: a step may carry `"debug": true` — `run.ts` then echoes that step's stdout (capped at 2000 chars) into the run log, and a failed `stdoutIncludes` assertion now prints the stdout it got instead of only "assertion failed". Diagnose a CI-only failure with an `["eval", "<js>"]` debug step that dumps DOM/scroll state at the exact failing point rather than reading tea leaves in the failure screenshot — the screenshot is taken 60s later, after the timeout, and cannot distinguish "never opened" from "opened then re-rendered". `test-results/` is now created at runner start (not only in the failure path), so a mid-flow `["screenshot", "test-results/x.png"]` step also works on a clean CI checkout where that dir is gitignored and absent (evidence: e2e/run.ts; e2e/lib/assert.ts `Step.debug`)

## Tool & Library Notes
<!-- Quirks, gotchas, and useful behaviors discovered about dependencies -->
- 2026-08-30: NEVER assume a live `localhost:3000`/`:3001` stack matches the hermetic no-provider-credential environment `e2e-web.yml`/AC-55-style flows target — a running dev stack (started for daily work, not by `scripts/e2e.sh`) can carry real provider keys. Check `curl -s localhost:3001/settings/secrets-status` before clicking any control that starts a real run/review; on this machine's dev stack it returned `{"anthropic":true,"openrouter":true,...}`, and clicking a flow-11-style "Run eval" against it made real, billed Anthropic/OpenRouter calls for ~80s before being caught and cancelled via `POST /eval-suite-runs/:id/cancel`. A flow written against the "no credential configured" assumption must be verified either against `scripts/e2e.sh`'s isolated stack or CI, never blindly against whatever dev stack happens to be up (evidence: this session's live run of e2e/specs/11-evals.flow.json's suite-run steps; GET /agents/:id/eval-runs showing a `running` row for 80+ real seconds, not the sub-second completion the credential-less code path implies from server/src/modules/eval/runner.ts's synchronous `secrets.get()` throw)
- 2026-08-30: the `Prompt assembly` click in flow 09 is one layout change away from breaking for real, independent of the CI mystery: at a **1280x720** viewport the section header lands at y=653..698, directly under the drawer's sticky "Copy raw output" footer, and agent-browser 0.35.1 refuses with `Element '[data-agent-browser-located='true']' is covered by <div> at its click point`. At 1280x577 and 800x600 the header is BELOW the viewport instead, so agent-browser scrolls it into view first and the click succeeds. Any e2e click on the lower half of the RunTraceDrawer is viewport-height-sensitive for this reason (evidence: local runs of the flow-09 tail at 800x600 / 1280x720 / 1280x577; client/…/RunTraceDrawer/RunTraceDrawer.tsx `footer=`)
- 2026-08-30: `.github/workflows/e2e-web.yml` installs agent-browser UNPINNED (`npm i -g agent-browser`), so the CI binary drifts from the local one with no signal in the log — on 2026-08-30 CI ran 0.35.1 while the dev machine had 0.33.2 (0.34.0 landed 08-10, 0.35.0 08-25). Before blaming a flow for a CI-only failure, check `npm view agent-browser time --json` against the run date; and to test a specific version locally without disturbing the global install: `npm i -g --prefix <scratch>/ab agent-browser@<v>` then put `<scratch>/ab/bin` first on PATH (evidence: .github/workflows/e2e-web.yml "Install agent-browser"; `agent-browser --version` 0.33.2 local vs 0.35.1 latest)
- 2026-08-30: the e2e failure artifact PNG is itself evidence — its pixel dimensions ARE the CI viewport (`file 09-project-context-fail.png` → `1280 x 577`). ## Recurring Errors & Fixes

- 2026-08-30: **ROOT CAUSE + CONFIRMED FIX for the six-run flow-09 failure** (supersedes the two "unexplained" 2026-08-30 entries under What Doesn't Work). `find text "<label>" click` does **not** scroll its target into view on the CI runner. The `Prompt assembly` header measures `y=653` in a 577-tall viewport with the drawer's scroller at `scrollTop=0`, so agent-browser dispatches the click at `cy=676` — outside the viewport — where it hits nothing and **still exits 0**. The DIAG probes on CI are byte-identical before and after the click (`open:false, scrollers:[[0,435,859],…]`), which is why every longer wait failed: nothing was ever going to open. The identical locator DOES auto-scroll on macOS (`y 653→277`, `scrollTop 0→376`, `open:true`), which is why it never reproduced locally — not against a production build, not on CI's own agent-browser version, not at CI's exact viewport. FIX: an explicit `["eval", "…el.scrollIntoView({block:'center'})…"]` step immediately before each click on a below-the-fold target; `block:'center'` also keeps it off the drawer's sticky footer. ALWAYS add that step before clicking anything in the lower half of a long scrollable panel — never assume the click scrolls. Verified: CI run 33312868145 green, probes `y:277 scrollTop:376 open:true labelInDom:true` (evidence: e2e/specs/09-project-context.flow.json "centre the … header"; CI runs 33312571731 red → 33312868145 green)
- 2026-08-30: a `find … click` that exits 0 is NOT evidence that anything was clicked. agent-browser reports success for a click dispatched at coordinates outside the viewport, and only raises `Element … is covered by <div> at its click point` when the point is inside the viewport and occluded. When a click "succeeds" but the next assertion fails, probe the target's `getBoundingClientRect()` against `innerHeight` before blaming the app, the data or the timing (evidence: the flow-09 DIAG probes; the covered-element error reproduced locally at a 1280x720 viewport)
