## What Works
<!-- Approaches, patterns, and solutions that have proven effective here -->
- 2026-08-23: confirmed fix for the PR-row click race — one `{ "cmd": ["wait", "--load", "networkidle"] }` step between `wait --url "/pulls"` and `find text "Add rate limiting to public API endpoints" click` retires it: four consecutive hermetic runs of the full suite went 9/9 after inserting it in 04, 05 and 09, against a 7/9-8/9-9/9 flap before. Flow 02 never flapped on the identical click because it happens to assert `wait --text` on the row title first — that `wait --text` was doing the guarding, not luck. RULE: a `find` whose target comes from a fetch needs either `wait --load networkidle` or a `wait --text` on the target between it and the `wait --url` (evidence: e2e/specs/04-pr-findings.flow.json:7, 05-pr-diff.flow.json:7, 09-project-context.flow.json:37; 4x `E2E_PG_PORT=5441 E2E_API_PORT=3111 E2E_WEB_PORT=3110 npm run e2e:hermetic`)
- 2026-08-23: a sidebar `find text "Conventions"|"Project Context" click` straight after `wait --url "/pulls"` is NOT the same race and needs no settle — the nav labels come from the static `vendor/ui/nav.ts` array rendered by `AppFrame`, so they exist as soon as the shell mounts, independent of any repo/PR fetch. Only a locator whose text arrives with API data has to be guarded; auditing flows 01-09 for the unguarded pattern turned up nothing beyond 04, 05 and 09 (evidence: client/src/vendor/ui/nav.ts:34; client/src/components/app-shell/AppShell.tsx:22; e2e/specs/08-conventions.flow.json:7, 09-project-context.flow.json:7)
- 2026-08-23: when a flow asserts a next-intl message that interpolates the repo, assert ONLY the invariant head of the string. `context.attachedCount` renders as `0 attached · 4 in acme/payments-api` (the panel passes `activeRepo.full_name`, falling back to `context.repoUnknown` = "the selected repository"), so `wait --text "0 attached"` / `"1 attached"` still distinguishes before from after while staying off both the full repo name and the U+00B7 separator — a flow file that stays ASCII apart from the one deliberate em dash is easier to keep byte-exact (evidence: client/messages/en/agents.json `context.attachedCount`; client/src/components/doc-attach/DocAttachPanel.tsx:174; client/src/app/agents/[id]/_components/AgentEditor/_components/ContextTab/ContextTab.tsx:44)
- 2026-08-23: the run-trace drawer hides prompt text behind TWO independent collapses, and a flow must click both or `wait --text` times out on body text that is simply not in the DOM: the `Prompt assembly` `TraceSection` is `defaultOpen={false}`, and then EACH `PromptBlock` segment is separately collapsed (`useState(false)`) and renders its `<pre>` only when open. Both headers are `div`s with `onClick`, not buttons, so `find text "<label>" click` is the right locator for both. Asserting the segment's LABEL passes with only the first click — that is what makes the second one easy to miss (evidence: client/…/RunTraceDrawer/_components/PromptBlock/PromptBlock.tsx:70 `{open && <pre…>}`; TraceBody.tsx `TraceSection … defaultOpen={false}`; cost one red hermetic run on e2e/specs/09-project-context.flow.json)
- 2026-08-23: `find text "<label>" click` DOES work for a clickable non-button card — the agent cards on `/agents` are plain `<div onClick>` wrappers, and clicking the inner text bubbles to the card and navigates. This does not contradict the 2026-08-05 entry below: that one is about real `<button>`s, whose text locator resolves to a wide ancestor. Rule of thumb: `find role button --name` for buttons, `find text … click` for div-with-onClick cards and sidebar links (evidence: e2e/specs/09-project-context.flow.json "open the agent editor"; client/src/app/agents/_components/AgentCard/AgentCard.tsx:29)

## What Doesn't Work
<!-- Failed approaches, dead ends, antipatterns to avoid -->
- 2026-08-23: `open {BASE}/` → `wait --url /pulls` → `find text "Add rate limiting to public API endpoints" click` with NOTHING between the last two is a race, and it is the single step behind the "failing set moves between runs" symptom below — three consecutive hermetic runs over the same specs failed it in 04+05, then 04+09, then 09 alone. `wait --url` returns as soon as the route commits, but the row text only exists after `GET /repos/:id/pulls` resolves, and the API logs a GitHub sync attempt (`GitHub PR sync skipped (no token / offline)`) on that request. Flows 04, 05 and 09 all carry this identical three-step opening. A `wait --load networkidle` or a `wait --text` on the row before the click is the fix; do NOT read a failure on this step as a broken locator (evidence: e2e/specs/04-pr-findings.flow.json:5-7, 05-pr-diff.flow.json, 09-project-context.flow.json:35-37; three runs of `E2E_PG_PORT=5441 npm run e2e:hermetic`)
- 2026-08-23: correction — the entry below quotes the badge as `0 of 4 attached`; the review fix for finding #8 reworded `context.attachedCount` to `{attached} attached · {total} in {repo}` and `context.missing` to `not in this repo`, and the flow now asserts `0 attached` / `1 attached`. The point the entry makes (the seed leaves `agent_docs` empty, so nothing is attached when the flow starts) is unchanged (evidence: client/messages/en/agents.json:104,109; e2e/specs/09-project-context.flow.json:27,29)
- 2026-08-23: a flow CAN assert inside `RunTraceDrawer`, but ONLY because the seed now carries a fixture run — one `agent_runs` row (`status='done'`) on PR #482 plus its `run_traces` document. The drawer mounts on `?trace=<runId>` and its openers render only for an `agent_runs` row, so before that row existed `GET /pulls/:id/runs` returned `[]` and nothing trace-shaped was reachable from a browser at all. Two consequences that still bite: NEVER hardcode the run id (`agent_runs.id` is `defaultRandom()`, so it differs every seed — open the drawer through the UI), and read the trace as a FROZEN artifact of a past run, independent of live `agent_docs` — the fixture trace reports `specs/idempotency-keys.md` as injected while the agent has nothing attached, which is deliberate and is what lets one flow assert both `0 of 4 attached` and a populated `Specs read` (evidence: server/src/db/seed.ts:208 `demoRunTrace` builds it through the real `assembleProjectContext`/`assemblePrompt`; client/src/app/repos/[repoId]/pulls/[number]/page.tsx:203; e2e/specs/09-project-context.flow.json)
- 2026-08-05: `find text "<label>" click` is NOT a reliable way to click a button — the text locator resolves to a wide ancestor whose click point can land under the sidebar, failing with "Element … is covered by `<aside>` at its click point". It fails even when the label is unique and visible. ALWAYS use `find role button click --name "<label>"` for buttons; keep `find text` for non-interactive assertions and for sidebar/nav text, which sits inside the aside and so is never covered (evidence: e2e/specs/08-conventions.flow.json Accept/Create skill/Cancel steps; reproduced with `agent-browser find text Accept click` against the conventions page)
- 2026-08-05: flows share ONE browser session and run in order, so a failure cascades into later flows and the failing SET moves between runs — three consecutive runs of the same suite failed 02, then 04+05, then 04 alone. NEVER conclude a flow is broken from a single run; re-run before diagnosing, and read a failure in flow N as possibly caused by flow N-1 leaving the session somewhere unexpected (evidence: three `./scripts/e2e.sh` runs over the unchanged specs 01-07)

## Tool & Library Notes
<!-- Quirks, gotchas, and useful behaviors discovered about dependencies -->
- 2026-08-23: `scripts/e2e.sh` runs `next dev` against the SHARED `client/.next` directory, so a stale or half-written dev cache breaks the hermetic suite in a way that reads as a broken assertion. Symptom: a mid-flow `wait --text` on document body text fails while the API answers 200, and the web log shows `Cannot find module './vendor-chunks/recharts.js'` plus `ENOENT ... .next/routes-manifest.json`, with the page route itself returning 500. `rm -rf client/.next` and re-run — the very same flow then passed every step. ALWAYS check the web-side stack trace before editing a flow that just started failing (evidence: hermetic run of 09-project-context.flow.json failing at "the preview renders the document's text"; scripts/e2e.sh:147 `pnpm exec next dev -p "$WEB_PORT"`)
- 2026-08-23: `find role <role> --name <n>` matches the accessible name as a **case-insensitive substring** by default (`--exact` opts out); the role itself always ignores case. That makes a `button` lookup ambiguous the moment a second control's name contains the same words — after attaching a document, `find role button --name "idempotency-keys.md"` matches both the document row and the "Move up: specs/idempotency-keys.md" IconBtn. Reach for the narrower role: the vendored `Checkbox` is a `<button role="checkbox">` wrapped in a `<label>`, and Chrome names it from that label, so `find role checkbox click --name "<file name>"` stays unique (evidence: `agent-browser find --help`; `agent-browser snapshot` on the agent Context tab → `checkbox "idempotency-keys.md" [checked=false]`; client/src/vendor/ui/kit/Checkbox.tsx:24)
- 2026-08-23: `agent-browser get url` reports the last **committed** navigation and goes stale after a client-side (App Router) navigation — it kept printing `/agents` for seconds after a card click had already pushed `/agents/<id>?tab=config`. `wait --url` polls the live URL and is correct; so is `eval "location.href"`. NEVER diagnose an SPA navigation with `get url` — you will conclude the click did nothing (evidence: probing the `/agents` card click against a local hermetic stack; `get url` → `/agents` while `eval location.href` → `/agents/7339…?tab=config`)
