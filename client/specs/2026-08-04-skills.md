# Spec: Skills as a first-class entity (client)

Studio UI for the server-side skills feature (`server/specs/2026-08-04-skills.md`):
create/edit/version a skill as standalone markdown, link it to agents with an
explicit order, import untrusted files through a preview-then-confirm flow,
and see its (correlation-only) impact in Stats. See that spec and
`.superpowers/sdd/dazzling-spinning-shore/context.md` for the "why" behind the
rules referenced below.

## Navigation

**Component:** `src/vendor/ui/nav.ts`.
**Behavior:** new **SKILLS LAB** group holding Skills and Agents —
`AgentsListView` already breadcrumbs "Skills Lab › Agents", so Agents moves
out of `WORKSPACE` into this group. Skills gets `gKey: "s"`, `href:
"/skills"`, `icon: "Sparkles"`; add `{ keys: "g s", label: "Go to Skills",
group: "Navigation" }` to `SHORTCUTS`. `activeKeyFor`
(`src/components/app-shell/helpers.ts`) already maps `/skills` →
`"skills"` — no change needed there.

## Data layer

**Component:** `lib/hooks/skills.ts`, `lib/hooks/agent-skills.ts` — the
only allowed way to reach the API (`client/CLAUDE.md`).
**Behavior:** follows `lib/hooks/agents.ts`'s `invalidateQueries(["skills"])`
+ `setQueryData(["skill", id])` pattern. `skills.ts`: `useSkills()`
(`["skills"]`), `useSkill(id)` (`["skill", id]`, `enabled: !!id`),
`useCreateSkill()` / `useUpdateSkill()` / `useDeleteSkill()`
(invalidate/set/remove as above), `useSkillVersions(id)`,
`useSkillVersionDiff(id, version)`, `useRestoreSkillVersion(id)` (also
invalidates `["skill", id, "versions"]` — a restore changes both the
current body and the version list), `useSkillStats(id)`. `agent-skills.ts`:
`useAgentSkills(agentId)` (linked skills in order), `useSetAgentSkills(agentId)`
(the server routes already exist; sends the full ordered `skill_ids`;
invalidates `["agent-skills", agentId]` and `["agent", agentId]`, since a
save may bump the agent's version per `agents/repository.ts`'s
`snapshotVersion`).

## Pure helpers

**Component:** `lib/skills/parse.ts`, `lib/tokens.ts` — no React, no
network, independently unit-tested.
**Behavior:**

```ts
parseSkillMarkdown(text): { name, description, body }
extractSkillFromArchive(bytes): { markdown, entry, skipped: string[] }
```

`parseSkillMarkdown` reads name/description from YAML frontmatter, falls
back to the first `h1` for the name, and strips frontmatter from the body.
`extractSkillFromArchive` uses `fflate.unzipSync`, preferring `SKILL.md`
and otherwise the first `*.md` entry; every non-markdown entry goes into
`skipped` and is never read or executed. Zip-bomb limits: a maximum entry
count, a maximum total decompressed size, and rejection of any entry path
containing `..`. `fflate` (~8 KB) is the only new dependency — chosen
specifically so archive unpacking can happen client-side (decision 9: the
server stays JSON-only, avoiding `@fastify/multipart` plus a server-side
zip dependency; preview-then-confirm is inherently a UI step anyway).

`estimateTokens(text): number` drives the token chip next to the skill body
editor. This is explicitly an **estimate**, not an exact count —
`js-tiktoken` is not pulled into the client bundle for it — so the chip
reads `~166 tokens` with a tooltip clarifying it is approximate, never
presented as an exact figure.

## Routes and component tree

**Component:** `app/skills/`, mirroring `app/agents/` (list on the left,
detail on the right, active tab in `?tab=`).
**Behavior:** `app/skills/page.tsx` renders `SkillsListView` with an empty
detail pane (`page.selectPrompt`); `app/skills/[id]/page.tsx` renders
`SkillsListView` + `SkillEditor`. Under `_components/`: `SkillsListView`
(list column: search, "Add Skill" dropdown), with children
`CreateSkillModal` (name, description, type, body) and
`ImportSkillDrawer` (file → parse → preview → confirm); `SkillCard` (name,
Toggle, description, type badge, source badge, footer "N agents" — the only
per-skill metric `GET /skills` carries; pull frequency and accept rate are
per-skill aggregates and live on the Stats tab, deliberately kept out of the
list query); `SkillEditor` (header: name, type, version chip, vetting badge,
"Run on evals" button; body: the five tabs below), with children
`ConfigTab`, `PreviewTab`, `EvalsTab`, `StatsTab`, `VersionsTab`. Each
folder follows the module convention — `Component.tsx`, `styles.ts`,
`constants.ts`, `helpers.ts`, `index.ts` — only the files it actually
needs.

## The five editor tabs

**Component:** `SkillEditor`, tab selected via `?tab=`.
**Behavior:** Evals is not implemented in this feature — only a disabled
placeholder (L06).
- **Config** — the editable form: name, description, type, skill body
  editor (see ConfigTab below).
- **Preview** — read-only `<Markdown>` render of the body, captioned
  "Rendered as the reviewing agent receives it" — literally the content
  that lands in `## Skills / rules`, not a separate rendering.
- **Evals** — `EmptyState` reading "coming in L06". The "Run on evals"
  button in the editor header is `disabled` with an explanatory tooltip;
  it is not wired to any endpoint.
- **Stats** — see StatsTab below.
- **Versions** — see VersionsTab below.

## ConfigTab — the skill body editor

**Component:** `SkillEditor/_components/ConfigTab`.
**Behavior:** the mockup calls for a filename chip (`<name>.md`), an
`unsaved` badge, a token counter, line numbers, and markdown highlighting.
Built as a transparent `<textarea>` layered over a highlighted `<pre>`
(the standard overlay trick, roughly 40 lines) plus a scroll-synced
line-number gutter. Highlighting is regex-only, covering just markdown
constructs (heading / bold / list / code) — no tokenizer.

**Deliberately not used: CodeMirror or Monaco.** The skill body is plain
markdown with no code-intelligence requirements, so pulling in a full
editor component is unjustified weight here. Acceptable fallback if the
overlay proves troublesome: a plain monospace `<textarea>` with a
line-number gutter and no highlighting — the Preview tab already renders
formatted markdown, so in-editor highlighting is a nice-to-have, not a
requirement.

Description field hint — the description is the skill's interface, so it
is worded as a direct instruction, not a topic label:

> The description is the skill's interface: one imperative sentence about
> what the skill makes the agent do. Write "List the uncovered branches…",
> not "About test coverage."

Saving a body change surfaces an optional "What changed" field that
becomes the new version's `label`.

## VersionsTab

**Component:** `SkillEditor/_components/VersionsTab`.
**Behavior:** one row per version: `v{n}` · label · date · `Diff` /
`Restore`. The current version carries a `Current` badge and has no action
buttons — it cannot be diffed against itself or restored onto itself.
`Diff` calls `GET /skills/:id/versions/:v/diff` and feeds the resulting
`patch` to the existing `DiffViewer` as a single synthetic `PrFile`
(`{ path: "<name>.md", patch }`) — `DiffViewer` already accepts `PrFile[]`
and only reads `.path`/`.patch`, so no new diff renderer is written.
`Restore` calls `POST /skills/:id/versions/:v/restore`; per the server
spec this always creates a new version rather than mutating history, so
the row list grows by one and the new row becomes `Current`.

## StatsTab

**Component:** `SkillEditor/_components/StatsTab`.
**Behavior:** four `MetricCard`s (USED BY, PULL FREQUENCY, ACCEPT RATE,
FINDINGS 30D), an "AGENTS USING THIS SKILL" list linking each entry to
`/agents/:id`, and a `Donut` chart for FINDINGS BY CATEGORY. Any `null`
metric renders as `—`, never `0%`. Under the tab heading, a permanent
caption (always present, not conditional on any metric being null — same
wording as the server spec's honesty requirement):

> Metrics are aggregated over the agents this skill is linked to right
> now. This is correlation, not attribution: a finding is not attributed
> to any one skill, and changing links rewrites the history.

## Import flow

**Component:** `ImportSkillDrawer`.
**Behavior:** `<input type="file" accept=".md,.zip">` → `lib/skills/parse.ts`
(`parseSkillMarkdown` / `extractSkillFromArchive`) → a preview screen
(name / description / type / rendered body, plus skipped non-markdown
archive entries labelled "not processed") → an "Import skill" button →
only then `POST /skills` with `source: 'imported_file'`. Nothing reaches
the network before the user confirms. The server independently forces
`enabled: false` for any non-`manual` source (server spec, Creation rule),
so the freshly imported skill always lands with a "needs vetting" badge
regardless of what the client sends — a file picked but never confirmed
never leaves the browser.

## Skills tab in the agent editor

**Component:** `AgentEditor/constants.ts`, `AgentEditor.tsx`, new
`AgentEditor/_components/SkillsTab/`.
**Behavior:** `TABS` gains `{ key: "skills", labelKey:
"editor.tabs.skills", icon: "Sparkles" }`. `AgentEditor.tsx` routes to the
new tab by `tab` (today it always renders `<ConfigTab>`); `?tab=` is
already wired. `SkillsTab` lists every skill in the workspace: a checkbox
marks it linked, a drag handle sets order, plus a filter box and a header
reading "{linked} of {total} enabled" with the `skills.orderHint` copy.
Any checkbox toggle or reorder calls `useSetAgentSkills` with the full
ordered `skill_ids` array (not a delta), matching how `POST
/agents/:id/skills` already behaves. Reordering uses native HTML5
`draggable` attributes on the rows — no new drag-and-drop dependency.

## i18n

**Component:** `client/messages/en/skills.json`.
**Behavior:** existing blocks `page`, `detail`, `drawer`, `file`,
`listItem`, `preview` mostly cover this feature already. Two more existing
blocks, `url` and `community`, are **not** used by this feature and must
stay regardless: decision 1 restricts import to file/zip only for this
lesson, but the URL-import and community-catalog copy those blocks carry
belongs to other lessons in the course — deleting them would break work
this feature has no visibility into.

New keys to add: `editor.tabs.{config,preview,evals,stats,versions}`,
`editor.runOnEvals`, `editor.runOnEvalsDisabled`, `config.*` (form field
labels + `descriptionHint` + `bodyTokens` + `unsaved`), `stats.*` (tile
headings + the correlation disclaimer), `versions.*` (`history`, `count`,
`current`, `diff`, `restore`, `restoredFrom`; the version label's placeholder
is `config.versionLabelPlaceholder`, shared with the Config tab),
`evals.comingSoon`, `listItem.source.imported_file`, `delete.*`. Every new
string goes into all locales (`client/CLAUDE.md`) — `en` is currently the
only one shipped.

**Correction landing alongside this feature:** `file.bodyHint` ("Pasted
content is wrapped as untrusted data — never executed as instructions"),
`file.success` ("stored as untrusted data"), and `preview.untrustedNotice`
("stored as data (delimiter-wrapped)") describe the starter's old,
pre-decision-2 behavior and directly contradict it — a skill body renders
unwrapped into `## Skills / rules` precisely so it takes effect; the
safeguard is procedural (`enabled: false` until a human vets it, decision
3), not a delimiter. A separate task is correcting these three strings
now. Do not reintroduce wording that says a skill body is "stored as
untrusted data" or "delimiter-wrapped" when touching these keys again —
that phrasing describes behavior this feature deliberately does not have.
