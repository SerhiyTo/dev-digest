# Spec: Skills as a first-class entity (server)

Today an agent is `provider + model + system prompt`. Every rubric or rule
lives buried inside one agent's system prompt and cannot be reused. This
feature makes a **skill** a standalone block of markdown instructions —
edited in the UI, versioned, stored in Postgres (DB is the source of truth),
and **linked to many agents with an explicit per-agent order**. A skill is
**text only**: no code, no tools, no execution. The order of the links is the
order of the blocks in the assembled prompt.

## What the starter already ships

**Behavior:** the starter ships half the infrastructure on purpose
(`server/CLAUDE.md`: "DB schema contains every table up front").
- DB — `skills`, `skill_versions`, `agent_skills` already in `0000_init.sql`
  (`src/db/schema/skills.ts`, `src/db/schema/agents.ts`).
- Contracts — `Skill`, `SkillType`, `SkillSource`, `AgentSkillLink` in
  `src/vendor/shared/contracts/knowledge.ts`.
- Agent-side link table — `linkedSkills` / `linkSkill` / `unlinkSkill` /
  `setSkills` / `skillIdsForAgent` in `src/modules/agents/repository.ts`.
- Agent routes — `GET/POST /agents/:id/skills` in
  `src/modules/agents/routes.ts`, already accepting an ordered `skill_ids`.
- Agent versioning — `agent_versions.config_json.skills` persists the
  ordered id list at each config snapshot (`agents/repository.ts`'s
  `snapshotVersion`).
- Engine — `ReviewInput.skills?: string[]` → `assemblePrompt` renders
  `## Skills / rules` (`reviewer-core/src/review/run.ts`,
  `reviewer-core/src/prompt.ts`).
- Trace — `PromptAssembly.skills` plus a dedicated `PromptBlock` in the
  trace (`src/vendor/shared/contracts/trace.ts`, client `TraceBody`).

**Missing:** the `skills/` server module entirely, and — critically —
passing skill bodies into `reviewPullRequest`. Without that wiring the
feature has no effect on a review no matter how much UI sits on top of it.

## Contract changes

**Component:** `src/vendor/shared/contracts/knowledge.ts`, mirrored
byte-identically in the same commit to
`client/src/vendor/shared/contracts/knowledge.ts`.
**Behavior:** `SkillSource` gains `imported_file` — the only import path
this feature ships. `skills.source` is a plain `text` column
(`src/db/schema/skills.ts`), not a Postgres enum, so widening the list needs
**no** SQL migration. `imported_url` and `community` stay in the enum
unused — other lessons rely on those values (decision 1); do not delete
them.

```ts
export const SkillSource = z.enum([
  'manual', 'imported_file', 'imported_url', 'extracted', 'community',
]);
```

New schemas: `SkillVersion` (adds nullable `label`, the feature's one
migration) and `SkillStats` (aggregates for the Stats tab, computed from
existing tables through the current `agent_skills` links only — see Stats
below).

```ts
export const SkillVersion = z.object({
  skill_id: z.string(),
  version: z.number().int(),
  body: z.string(),
  label: z.string().nullish(),
  created_at: z.string(),
});

export const SkillStats = z.object({
  used_by: z.number().int(),
  agents: z.array(z.object({ id: z.string(), name: z.string() })),
  pull_frequency: z.number().nullish(),
  accept_rate: z.number().nullish(),
  findings_30d: z.number().int(),
  findings_by_category: z.record(z.string(), z.number().int()),
});
```

## Migration

**Component:** `src/db/schema/skills.ts` — `skillVersions` gets a nullable
`label` column, the feature's only schema change.
**Behavior:** `label: text('label')`, then **only** `pnpm db:generate` →
`pnpm db:migrate`. Never hand-edit `src/db/migrations/*.sql`
(`server/CLAUDE.md`). Next migration number is `0012_*` (`0011` already
exists in this working tree for an unrelated change).

## Module layout

**Component:** new `src/modules/skills/`, one-to-one with
`src/modules/agents/` (onion: `routes.ts → service.ts → repository.ts`,
pure mappers in `helpers.ts`).
**Behavior:** `routes.ts` (Zod request schemas + registration), `service.ts`
(workspace scope, versioning, restore), `repository.ts` (Drizzle access to
`skills`/`skill_versions`), `stats.ts` (Stats tab SQL aggregates), `diff.ts`
(unified diff of two bodies, wraps jsdiff), `helpers.ts` (`toSkillDto`,
`toSkillVersionDto`, `isBodyChange`), `constants.ts`
(`INITIAL_SKILL_VERSION`, `STATS_WINDOW_DAYS = 30`). `stats.ts` and
`diff.ts` are split out because they are a different kind of responsibility
from CRUD/versioning: `stats.ts` is read-only cross-table aggregation with
its own join chain, `diff.ts` is a pure, independently testable text
algorithm — neither belongs in a service whose other methods mutate rows.
Registered in `src/modules/index.ts`: one import + one entry in `modules`.

## Routes

**Component:** `src/modules/skills/routes.ts`.
**Behavior:** workspace-scoped through `getContext`; a missing skill 404s
via `NotFoundError` — mirrors `agents/routes.ts` exactly.

| Method | Path | Behavior |
|---|---|---|
| `GET` | `/skills` | List the workspace's skills, each with `used_by` attached via one `GROUP BY` (not N+1 per-skill queries) |
| `GET` | `/skills/:id` | Fetch one skill |
| `POST` | `/skills` | Create: `name`, `description`, `type`, `body`, `source?`, `enabled?` |
| `PUT` | `/skills/:id` | Update fields / toggle `enabled`; accepts an optional `version_label` |
| `DELETE` | `/skills/:id` | Delete; `agent_skills` rows cascade (`schema/agents.ts`) |
| `GET` | `/skills/:id/versions` | Version history, newest first |
| `GET` | `/skills/:id/versions/:v/diff` | `{ patch: string }` — unified diff of version `v` against the current body |
| `POST` | `/skills/:id/versions/:v/restore` | Creates a new version carrying version `v`'s body |
| `GET` | `/skills/:id/stats` | `SkillStats` |

## Creation rule

**Component:** `src/modules/skills/service.ts` — enforced in the service,
not the route.
**Behavior:** `source ?? 'manual'`; if `source !== 'manual'`, force
`enabled = false` (decision 3). The server is the gate, not the client: a
caller that forgets to send `enabled: false` on an import still gets a
disabled skill back.

## Versioning rule

**Component:** `src/modules/skills/repository.ts`, mirrors
`agents/repository.ts`'s `snapshotVersion`/`isConfigChange` pattern.
**Behavior:** a changed `body` bumps `version` by 1 and writes a snapshot
into `skill_versions` (`body` + `label`). A change to only `name` /
`description` / `type` / `enabled` does **not** bump the version and writes
no snapshot. The Config tab surfaces the rule implicitly: the version-label
field (`config.versionLabelLabel`) appears only once the body differs from
the saved one, so a name-only edit never offers to label a version.

## Restore semantics

**Behavior:** restore never rewrites history. `POST
/skills/:id/versions/3/restore` while the skill is currently at v5 creates
a **new v6** whose body is v3's body, auto-labelled `Restored from v3`. No
operation deletes or overwrites an existing `skill_versions` row.

## Stats

**Component:** `src/modules/skills/stats.ts`.
**Data:** entirely existing tables — no new `run_skills` table (decision
6). Join chain: `agent_skills(skill_id) → agents → agent_runs →
reviews(run_id) → findings`.

| Tile | Definition |
|---|---|
| **USED BY** | `COUNT(*) FROM agent_skills WHERE skill_id = $1` — exact |
| **AGENTS USING THIS SKILL** | same join to `agents` (id + name, for "Open" links) |
| **PULL FREQUENCY** | `runs_of_linked_agents / all_workspace_runs` — "how often this skill is actually in play". `null` when the workspace has no runs at all (never `0%`) |
| **ACCEPT RATE** | `accepted / (accepted + dismissed)` over findings from reviews by linked agents. `null` when nothing has been accepted or dismissed yet |
| **FINDINGS (30D)** | `COUNT(findings)` from reviews by linked agents, last `STATS_WINDOW_DAYS` (30) days |
| **FINDINGS BY CATEGORY** | `GROUP BY findings.category` over the same set — these are **counts**, not dollars (the mockup's `$52.00` is an unrelated placeholder) |

**Behavior — honesty requirement, not optional:** a finding does not know
which skill caused it, and no history of link changes is kept (decision 6).
The Stats tab therefore carries a permanent caption under its heading:

> Metrics are aggregated over the agents this skill is linked to **right
> now**. This is correlation, not attribution: a finding is not attributed
> to any one skill, and changing links rewrites the history.

Every nullable metric above renders as `—` in the UI, **never** `0%` — the
route must pass `null` through rather than coerce it to zero.

## Prompt wiring — the core of the feature

**Component:** `src/modules/reviews/run-executor.ts` (new call site) and
`src/modules/reviews/helpers.ts` (new helper).
**Behavior:** `ReviewRunExecutor` already holds `private agents:
Container['agentsRepo']`, so `this.agents.linkedSkills(agent.id)` needs no
new DI wiring.

```ts
/** Bodies of the enabled linked skills, in link order. */
export function renderSkillBlocks(links: LinkedSkillRow[]): string[]
```

filters to `l.skill.enabled` (decision 4: enabled AND linked) and maps each
to `### ${l.skill.name}\n${l.skill.body}`.

In `executeRuns`, immediately before the `reviewPullRequest` call inside
`runOneAgent`:

```ts
const links = await this.agents.linkedSkills(agent.id);
const skills = renderSkillBlocks(links);
runLog.event('info', `skills: ${skills.length} attached`, {
  attached: links.filter((l) => l.skill.enabled).map((l) => l.skill.name),
  skipped: links.filter((l) => !l.skill.enabled).map((l) => l.skill.name),
});
...(skills.length ? { skills } : {}),
```

matching the omit-when-empty contract already used for `callers` and
`repoMap`. From there `assemblePrompt` places the block under `## Skills /
rules`, `PromptAssembly.skills` lands in the persisted trace, and the
client's `TraceBody` renders it as its own `PromptBlock`. An empty array
means no section is added to the prompt, so a disabled skill is invisible
in the trace: `prompt_assembly.skills` is `null` and no `## Skills / rules`
section exists — this is the mechanism behind the control experiment. It
stays visible in the run log on purpose: the `skills: N attached` event
always lists the disabled links under `skipped`, so the log explains *why*
the trace has no block.

Skill bodies render unwrapped into `## Skills / rules`, **not** inside the
engine's `<untrusted>` delimiter: `INJECTION_GUARD`
(`reviewer-core/src/prompt.ts`) tells the model to ignore instructions
found inside those delimiters, which would make every skill inert,
including the one imported live for the control experiment (decision 2).
Protection against a hostile imported skill is procedural instead —
`source !== 'manual'` forces `enabled: false` (decision 3) — not syntactic.

## Seeded skills and agents

**Component:** `src/db/seed.ts`, idempotent like the rest of the seeder.
**Behavior:** skills (`source: 'manual'`, `enabled: true`):
`test-coverage-rubric` (`rubric` — uncovered branches and edge cases),
`flaky-test-signals` (`custom` — timing dependencies, shared state, real
network calls), `api-contract-compat` (`convention` — route signature
compatibility, required fields, response codes). Agents, each with an
explicitly ordered link set: **Test Quality Reviewer** →
`test-coverage-rubric` (order 0), `flaky-test-signals` (order 1); **API
Contract Reviewer** → `api-contract-compat` (order 0).

Deliberately not seeded: `mock-overuse-gate` — imported live through the UI
import flow as a demo of the untrusted-import path, not part of the
idempotent seed data. Its fixture (`SKILL.md` plus non-markdown files, to
prove the "skipped" list works) lives under `docs/agent-prompts/skills/`.

Prompt templates for the two new agents (`test-quality-reviewer.md`,
`api-contract-reviewer.md`) follow the format of the existing
`security-reviewer.md` / `performance-reviewer.md` in `docs/agent-prompts/`.
The seeded skill bodies live under `docs/agent-prompts/skills/` as the
single source of truth the seeder reads from — the same content a developer
could paste into a manually created skill.

## Server tests

**Component:** `server/test/`.
**Behavior:**
- `skills.it.test.ts` — CRUD; a changed `body` bumps the version and writes
  a snapshot, a changed `name` alone does not; `source !== 'manual'` forces
  `enabled: false`; restore creates a **new** version and never rewrites
  history.
- `skills-stats.it.test.ts` — aggregates: `null` (not `0`) when the
  workspace has no runs, `used_by` does not double-count, categories group
  correctly.
- `skills-diff.test.ts` — pure unified diff of two bodies.
- `reviews-helpers.test.ts` — extended for `renderSkillBlocks`: link order
  is preserved, disabled links are filtered out, an empty input returns
  `[]`.
- `routes-smoke.test.ts` — the new routes appear in the route registry.
